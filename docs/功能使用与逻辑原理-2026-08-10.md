# 对话知识副驾驶：功能使用与逻辑原理

> 文档生成时间：2026-08-10 09:58:42（UTC+08:00，Asia/Shanghai）  
> 对应项目版本：`knowledge-copilot 0.1.0`  
> 项目位置：`E:\Coding小项目\capture-conversation-knowledge\knowledge-copilot`

## 1. 先用一句话理解它

这套程序是一个运行在主对话旁边的“知识状态服务”：AI宿主或调试页面在一轮对话结束后，把用户消息、助手回答和必要的工具结果提交给它；它识别这一轮新增、修正或失效的知识，保存成可追踪的卡片，并在需要时重新阅读已保存的完整对话，导出学习笔记、思维导图或JSON数据。

它不负责替代ChatGPT、Codex、Claude或其他主助手，也不会在没有宿主调用、Hook或用户授权时监听对话。

## 2. 它解决的核心问题

普通AI对话通常只有一条主线：把事情做完。例如完成脚本、备份ESP32固件或排查网络错误。在这个过程中，用户可能成功完成了操作，却没有系统理解：

- 为什么要这样做；
- 命令实际改变了什么；
- 哪些只是日志噪声；
- 结论依据是什么；
- 之前的假设为什么被推翻；
- 哪些问题值得以后深入学习。

Knowledge Copilot把这部分内容放入独立的知识旁路。主对话继续完成任务，知识服务维护另一套可持续更新的数据。

## 3. 目前可以做什么

### 3.1 创建学习会话

每次知识沉淀从一个`Session`开始。会话记录：

- 标题；
- 当前状态：`active`、`paused`或`ended`；
- 捕获范围：全部话题或指定话题；
- 来源宿主；
- 创建和更新时间；
- 最后处理到的真实轮次游标。

### 3.2 捕获一轮完整对话

一次捕获至少接收：

```text
用户消息 + 助手回答
```

还可以包含：

```text
工具观察结果 + 宿主轮次引用 + 幂等键 + 来源宿主
```

程序不会按token实时窃听，而是在“一轮已经完成并且结果足够解释”后处理。

### 3.3 维护知识卡片

当前支持七类知识卡片：

| 类型 | 含义 |
|---|---|
| `concept` | 概念、定义和关键区别 |
| `principle` | 原理、原因、约束和取舍 |
| `method` | 方法、标准和可重复步骤 |
| `operation` | 有学习价值的命令或操作 |
| `framework` | 层级、流程和决策框架 |
| `correction` | 被验证、修订或推翻的认识 |
| `learning_debt` | 当前不宜展开、但值得以后学习的问题 |

卡片不是只增不改的便签。系统支持：

| 事件 | 作用 |
|---|---|
| `add` | 创建新知识单元 |
| `revise` | 新证据补充或修订已有卡片 |
| `merge` | 合并重复或高度重叠的卡片 |
| `supersede` | 用新结论替换已被推翻的旧结论 |
| `discard` | 废弃噪声、重复项或错误残留，但保留历史 |
| `status_change` | 标记已掌握、待复习或忽略，不改变知识事实本身 |

### 3.4 捕获操作知识

对ESP32、编程、配置和排障场景，系统不会简单丢弃“执行细节”。它区分：

- 重复进度、无意义输出等执行噪声；
- 改变或检查设备、文件、代码、配置和诊断状态的有价值操作。

一张操作卡片可以记录：

```text
操作/命令
→ 实际作用
→ 当前目的
→ 底层机制
→ 前置条件
→ 验证方法
→ 风险
→ 可逆性
```

例如`esptool read-flash`会被解释为：设备Flash没有被改写，但本地备份文件被创建或覆盖；“命令成功”也不自动等于“备份有效”，还需要检查文件大小、哈希或进行二次读取比对。

### 3.5 暂停、恢复和只看新增

- 暂停后，显式提交的轮次仍可以保存，从而保持真实边界；但不会生成知识卡片。
- 恢复时返回数据库中的真实`resume_from_cursor`。
- “只看新增”使用卡片保存时的`updated_cursor`查询，而不是让前端猜测哪些内容是新的。

### 3.6 导出学习材料

当前支持三种格式：

- Markdown学习笔记；
- Mermaid思维导图；
- JSON完整导出。

Markdown不是按照卡片创建时间复制粘贴，而是按下面的知识依赖顺序重组：

```text
知识框架
→ 底层原理
→ 核心概念
→ 方法
→ 操作原理与验证
→ 纠错路径
→ 待深挖
```

旧的、已替换的冲突结论不会继续作为当前事实出现。

## 4. 最简单的使用方法

### 第一步：进入项目

```powershell
cd E:\Coding小项目\capture-conversation-knowledge\knowledge-copilot
```

### 第二步：第一次安装和初始化

```powershell
npm.cmd ci
npm.cmd run db:init
npm.cmd run build
```

### 第三步：用Mock模式启动

Mock模式不需要模型API Key，适合现在理解和验证系统。

```powershell
$env:KNOWLEDGE_COPILOT_EXTRACTOR='mock'
npm.cmd start
```

服务默认只监听本机：

```text
http://127.0.0.1:3210
```

### 第四步：打开知识面板

在浏览器中打开：

```text
http://127.0.0.1:3210
```

然后：

1. 输入标题并创建会话；
2. 展开“开发调试：提交一轮”；
3. 输入用户消息和助手回答；
4. 点击“捕获完成轮次”；
5. 查看“本轮新增”和“全部知识”；
6. 展开卡片查看来源、操作机制和风险；
7. 点击导出Markdown、Mermaid或JSON。

可使用下面的测试内容：

```text
用户消息：
运行 esptool read-flash 保存 backup.bin

助手回答：
读取完成。这个命令没有改写设备Flash，但在本地创建了备份文件；下一步检查文件大小和哈希。
```

### 第五步：运行自动演示

```powershell
npm.cmd run demo
```

这个命令会自动创建一个ESP32学习会话、捕获一轮操作、输出卡片和Markdown笔记。

## 5. 一轮对话在内部如何流转

```text
1. 宿主或调试页提交完整轮次
                    ↓
2. KnowledgeService检查Session是否存在
                    ↓
3. 根据宿主引用/显式key/内容哈希检查重复提交
                    ↓
4. 脱敏并保存Turn，真实cursor加1
                    ↓
5. 如果Session已暂停：停止提取，但保留轮次边界
                    ↓
6. 如果Session处于active：调用KnowledgeExtractor
                    ↓
7. 用v2 Zod Schema验证提取结果
                    ↓
8. 在SQLite事务中应用卡片生命周期事件
                    ↓
9. 返回新增、修订、合并、替换、学习债务和真实cursor
                    ↓
10. 面板按真实状态刷新
```

这条链路的核心入口是`KnowledgeService.capture()`。

## 6. 为什么重复提交不会不断产生卡片

捕获工具优先使用以下标识判断同一轮是否已经处理：

1. 调用方明确提供的`idempotency_key`；
2. 宿主提供的`source_reference`；
3. 用户消息、助手回答和工具观察的稳定SHA-256哈希。

SQLite对同一Session下的幂等键设置唯一约束。重复提交时，程序返回第一次保存的轮次和事件，并标记：

```json
{"idempotent_replay": true}
```

这就是“同一轮不会反复新增相同卡片”的基本保障。

## 7. 卡片是如何被更新的

### 新增

提取器发现新的独立知识，创建`revision = 1`的卡片。

### 修订

同一知识获得更充分的解释或证据时，保留`card_id`，增加`revision`，把新版本写入当前卡片表，同时把版本快照写入修订历史。

### 合并

相似卡片合并到一个保留身份的卡片中，来源记录会合并；被合并卡片进入`discarded`状态，不会从历史中物理消失。

### 替换

后续证据推翻旧结论时：

```text
旧卡片 → lifecycle=superseded
新卡片 → lifecycle=active，并通过supersedes指向旧卡片
```

因此“网络故障”和“系统时钟导致TLS失败”不会同时作为两个当前事实存在。

### 废弃

噪声、重复项或不再可靠的残留会被标记为`discarded`。这保留审计历史，又不污染当前知识视图。

## 8. SQLite里保存了什么

数据库默认位置：

```text
knowledge-copilot/data/knowledge-copilot.sqlite
```

主要数据表：

| 表 | 用途 |
|---|---|
| `schema_migrations` | 记录已经执行的数据库迁移 |
| `sessions` | 学习会话和真实游标 |
| `turns` | 用户消息、助手回答、工具观察和幂等键 |
| `cards` | 每张卡片的当前版本 |
| `card_revisions` | 卡片的不可变修订历史 |
| `card_events` | 每次新增、修订、合并、替换等事件 |
| `exports` | 已生成的导出及其来源cursor |

`cards`像“当前状态”，`card_revisions`和`card_events`像“历史账本”。这样既能快速展示当前卡片，也能查看结论如何变化。

## 9. Mock提取器和真实模型提取器的区别

### MockKnowledgeExtractor

- 不访问外部API；
- 不需要API Key；
- 根据测试关键词产生确定性结果；
- 能演示ESP32、短视频、技术排障、Excel、修订、合并和废弃；
- 主要用于自动测试、UI演示和流程验证。

Mock模式证明的是“系统闭环可以工作”，不代表它已经能理解任意自然语言对话。

### LLMKnowledgeExtractor

- 调用可配置的OpenAI-compatible `/chat/completions`端点；
- 模型名称、Base URL和Key由环境变量提供；
- 模型输出必须符合v2卡片事件Schema；
- 输出无效时会提供错误反馈并有限重试；
- 最终仍不合法时抛错，卡片事务回滚；
- 日志不会打印API Key。

配置示例：

```powershell
$env:KNOWLEDGE_COPILOT_EXTRACTOR='llm'
$env:KNOWLEDGE_COPILOT_BASE_URL='https://你的兼容端点/v1'
$env:KNOWLEDGE_COPILOT_API_KEY='你的密钥'
$env:KNOWLEDGE_COPILOT_MODEL='你的模型ID'
npm.cmd start
```

当前真实模型提取器已经实现，但还需要用你实际选择的模型进行效果评估和提示策略迭代。

## 10. MCP Server在这里起什么作用

MCP Server是核心系统与AI宿主之间的标准接口。它让不同宿主可以调用同一套能力，而不需要让知识引擎依赖ChatGPT、Claude或WorkBuddy。

当前主要工具：

| MCP工具 | 用途 |
|---|---|
| `start_learning_session` | 创建会话 |
| `capture_conversation_turn` | 捕获完整轮次 |
| `get_learning_session` | 读取会话和当前状态 |
| `list_knowledge_cards` | 查询全部或真实cursor后的卡片 |
| `get_knowledge_card` | 查看卡片和修订历史 |
| `revise_knowledge_card` | 人工修订卡片 |
| `change_capture_status` | 暂停、恢复、结束或缩小范围 |
| `change_card_learning_status` | 标记已掌握、待复习或忽略 |
| `list_learning_debts` | 查询待深挖内容 |
| `export_learning_package` | 导出Markdown、Mermaid或JSON |
| `open_knowledge_panel` | 请求支持MCP Apps的宿主打开知识面板 |

Server提供两种连接方式：

- `stdio`：适合本地AI宿主启动子进程；
- Streamable HTTP：适合调试页、网络客户端或未来远程部署。

## 11. 知识面板如何工作

知识面板有两种运行形态，但使用同一份前端代码。

### 独立预览页

直接打开`http://127.0.0.1:3210`。前端通过HTTP接口调用`KnowledgeService`，适合尚未接入AI宿主时调试。

### MCP App View

支持MCP Apps的宿主调用`open_knowledge_panel`后，读取：

```text
ui://knowledge-copilot/panel.html
```

面板在宿主iframe中通过MCP Apps桥接调用Server工具。

如果某个宿主不支持MCP Apps，MCP工具仍然可以工作，只是不能假定它会显示相同的内嵌面板或固定侧栏。

## 12. 目前哪些部分是真正可用的

### 已实现并验证

- Mock模式端到端闭环；
- SQLite初始化、保存和重启恢复；
- 卡片Schema与生命周期；
- 真实cursor与幂等；
- stdio MCP Server工具调用；
- HTTP服务；
- 独立知识面板；
- Markdown、Mermaid和JSON导出；
- 类型检查、单元测试、集成测试和构建。

### 已实现但还需真实环境验证

- LLM提取效果；
- 在Codex中重新安装插件后的真实调用；
- 在具体MCP Apps宿主中的iframe渲染和交互；
- Claude和WorkBuddy适配配置。

### 当前没有实现

- 无授权被动监听全部聊天；
- 跨任意宿主通用的固定侧栏；
- 公网部署、OAuth和多用户隔离；
- 生产级数据库加密和完整数据删除界面；
- 自动判断所有陌生领域的高质量知识；
- 完全基于LLM的深度最终重构评测。

## 13. 推荐的理解与体验顺序

如果你是第一次接触这套代码，建议不要马上配置真实模型或宿主插件。按下面顺序体验：

1. 运行`npm.cmd run demo`，观察一轮输入如何变成卡片和笔记；
2. 启动浏览器面板，手工提交ESP32示例；
3. 测试暂停、恢复和只看新增；
4. 连续提交“错误假设→验证推翻”的排障示例；
5. 运行`npm.cmd run test:mcp`，确认MCP工具层工作；
6. 最后再选择真实模型和真实宿主进行接入。

## 14. 建议下一阶段开发什么

最合理的下一阶段不是继续堆功能，而是验证两件关键事情：

1. **知识质量**：用真实模型跑一批非关键词化对话，评估卡片准确率、重复率、错误替换和操作噪声过滤。
2. **真实宿主体验**：在一个明确支持当前MCP/MCP Apps能力的宿主中完成安装、逐轮调用和面板渲染。

通过这两步后，再考虑远程部署、用户认证、跨会话知识地图、复习计划和生产级隐私能力。
